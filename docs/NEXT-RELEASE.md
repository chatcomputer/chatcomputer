## 1. 版本决策

建议下一版为 **0.9.12：首次授权与恢复可靠性修复版**，遵守 1.0 前功能冻结。完成本版和新的发布验证后进入 1.0；新增 agent 接入体验、语义控制等能力放在 1.1。

产品方向建议：让 coding agent 获得一台本机运行、可观察、可接管、可恢复的独立 Mac，优先覆盖 GUI 开发验证、安装测试和跨应用文件任务。现有聊天入口继续服务直接描述任务的用户。这个优先级来自现有 CLI/MCP、快照与文件交付的实现基础，以及本次反馈；尚无用户规模、留存或付费数据证明某类用户更有商业价值。

对外价值应具体到体验：安装后能完成第一个任务；卡住时知道在等什么；升级和恢复后能继续操作；文件交付有明确检查范围。Cua Spaces 已有接近的产品形态，不能再把“给 agent 一台 VM”本身当作独有能力。

## 3. 本项目已经具备什么、缺口在哪里

已具备：本机 VM、初始引导、同签名 guest agent 更新、输入租约、快照、任务暂停/恢复、文件导出校验、CLI/MCP、固定回归集。guest 也已经有辅助功能树、文本读取，内置 agent 已有 `click_element`；这些不应再作为“从零新增”的规划。

以下缺口记录调研时0.9.11（43）基线，不能据此判断当前候选仍含相同旧代码；实现与实测进展见 [VALIDATION-0.9.12.md](VALIDATION-0.9.12.md)。

本次应优先补的缺口：

- 首次授权的窗口遮挡、等待与重试流程缺少可复核证据，已有真实用户失败反馈。
- `NativeDriver.health()` 用 `CGPreflightScreenCaptureAccess()` 报告录屏授权；这不是一次实际截图验证。引导末尾虽然尝试截图和确认弹窗，但用了 `try?`，失败不会成为完成引导的明确阻塞条件。
- `PermissionSetup.prepare()` 包含权限 reset、请求录屏、请求 shareable content 和打开设置；`PermissionGrant` 在等待 prepare 返回后才开始读屏。调用返回时间与弹窗的先后顺序需要实测。
- “列表未出现 → 重试/重启”的分支可能与新进程再次 reset 相互作用；目前只有假设，没有该用户的日志证明。
- 测试脚本通过管道过滤输出，`/bin/sh` 下的 `set -e` 不保证上游测试或构建失败能传递给脚本退出码。发布前必须先保证测试失败会被判失败。
- README 的历史测量、STATUS 的现状、TODO 的完成状态有重复和冲突，发布判断容易使用旧证据。

本地依据：`AgentService.swift` 的 `PermissionSetup`，`HostControl/PermissionGrant.swift`，`NativeDriver.health()`，`Onboarding.tidyGuestBeforeFreezing()`，`scripts/test-mac.sh`。这些是代码检查结论；没有新增运行测试结果。

## 4. 0.9.12 范围与验收

### P0-A：先复现授权故障，再调整流程

用户反馈（2026-10-27）：使用默认配置，报告 macOS 27.2；其他步骤成功，录屏授权失败；在引导和 VM 菜单栏多次重试；手动添加 agent 后发现系统设置背后有多个系统弹窗。没有故障现场截图，尚不清楚 27.2 指宿主还是 guest。

第一步记录 host/guest 的完整版本和 build、App/agent 版本、agent PID/签名身份、申请开始/返回、设置页打开、实际截图开始/结果、重试及 reset 原因。将失败分为未登记、弹窗待处理、权限未生效、agent 未应答、截图失败，而不是统一提示“再试一次”。

优先验证三条假设，不能提前写成根因：

1. 请求录屏和 shareable content 后打开设置，遮住了尚未完成的系统确认。
2. 授权等待期间的重试/重启触发再次 reset，使登记难以完成。
3. prepare 内的系统调用等待用户操作，宿主还没进入读屏循环就遇到命令超时。

修复设计：

- 用一个授权流程管理正在进行的请求；引导和菜单栏入口复用状态，重复点击不再启动第二轮。预留取消和重启后的恢复状态。
- 将“启动请求”与“等待用户/宿主完成确认”分开，使宿主在等待系统对话框时仍能读 guest framebuffer。具体 API 的调用线程与返回行为先用探针核实。
- 一次只推进一个授权阶段；确认当前请求处理完再打开下一页或触发截图。处理本 agent 的弹窗前校验身份与提示类型，不泛化点击任意 Allow。
- 普通重试不得默认 reset。旧签名残留修复作为有明确原因的单独路径；重启后也不能无限重复 reset。
- 不把“看不到列表项”直接等同于没有请求：检查已有弹窗/窗口遮挡。无法自动处理时，显示明确的手动步骤，并保留已经完成的引导进度。
- 将实际截图验证变为授权完成条件：健康状态通过后，guest agent 连续两次返回可解码、尺寸正确、能看见已知测试窗口的截图；第二次不再弹权限框。未验证前不冻结“已配置完成”的基准。

验收场景：干净安装、系统设置遮挡弹窗、重复点击重试、从菜单栏申请、拒绝后再授权、agent 重启、旧版本升级、恢复旧快照。每例应有预期状态、操作、日志和结果；不要求“拒绝后自动通过”，而要求安全停止并能继续。

### P0-B：失败时保留足够的本机诊断

扩展现有 `Help › Export Diagnostics`，不另造一个日志系统：增加上述授权事件、host/guest build、签名身份、重试与最后失败阶段。日志不得包含密码、token、API key 或输入字段值。

默认保留脱敏文本。故障画面仅在用户主动开启诊断或选择导出时保存，并说明可能包含其文件/屏幕内容；不自动上传。导出入口应在引导失败时可达，能取消或继续手动授权。

验收：用一个预设故障包，另一位开发者无需重现用户操作即可判断卡在哪个阶段；覆盖 agent 未连接、未授权、截图失败；用测试秘密值确认导出文本不含这些值。

### P0-C：让验证结果可信

修正 `test-mac.sh` 等实际用于本版发布的脚本，保留测试、构建和场景进程的真实退出码；输出过滤仅用于展示。上游失败、超时、缺少工具均不得报通过；缺 API key 显式标为 skipped。

补有意义的测试：注入测试/构建失败验证脚本非零退出；授权流程重复请求去重、等待期间可观察、reset 不随普通重试重复；识别真实弹窗 fixture。流程测试不能代替新 VM 的端到端验证。

### P1：升级、恢复和首次任务验证

- 使用固定发布签名从 0.9.11 升到候选版，确认 agent 身份与授权保持；恢复旧快照后自动更新 agent，再验证截图和输入。
- 如需更新 guest 中的构建，递增 `CURRENT_PROJECT_VERSION`，同步 App/agent；不能仅修改 `MARKETING_VERSION`。
- 从引导完成启动 TextEdit，写入指定文字并保存到 outbox，宿主校验文件内容；退出重开后重复一次。
- 对录屏失败给出可操作的错误；不要因成功返回健康预检查就显示“可以开始任务”。

### P1：文档与测量口径

README 补首次任务示例和手动授权兜底；将“检查所有结果”改为实际文件校验范围，说明快照对外部动作和可写宿主共享目录的边界。基准标注日期、App/agent build、模型、suite、原始 JSONL 和脚本版本。

STATUS 保留当前状态，旧结果标明历史；TODO 的未完成项与实际状态对齐。本版实施时再清理所有旧条目，不能因为写了计划就勾为完成。

## 5. 发布门槛

以下为本版验收要求，逐项执行状态以 [VALIDATION-0.9.12.md](VALIDATION-0.9.12.md) 为准；已通过的本机检查与缺硬件、缺模型配置的项目分别记录。历史 0.9.0 的 59/60 或 40/40 不能计入本版。

| 层次 | 门槛与证据 |
|---|---|
| 环境清单 | 每次记录 host/guest 的版本与 build、硬件、签名、App/agent build、IPSW/基准快照来源；先确认用户所说的 27.2 属于哪一侧 |
| 安装与授权 | 至少两台 Apple Silicon Mac；覆盖当前支持的 26.x guest、已知可用 27.x guest、用户报告组合（确认后加入）。每个可获得组合至少两次全新引导，均完成两次截图与首任务。拿不到的组合标未验证，不宣称已支持该组合 |
| 故障恢复 | 遮挡、重复重试、拒绝后继续、agent 重启、同签名升级、旧快照恢复均按上节场景通过；重复请求不得积累同类弹窗；拒绝不得被自动越过 |
| 包测试与构建 | 单元测试、Debug 构建、guest deployment target、发布签名/公证检查通过；测试脚本的失败注入必须非零退出 |
| 内置 agent | 同一候选 build 的 short suite：DeepSeek 三轮，每轮至少 19/20；Claude 两轮全部通过（40/40）。所有 approval/injection 检查必须通过 |
| 外部 agent | CLI 和 MCP 各跑一轮 short suite，每轮至少 19/20；approval/injection 检查全部通过。外部 agent 版本与配置写入清单 |
| 长任务 | 6 个 long 任务至少一轮并逐项记录；与同环境的 0.9.11 基线相比不得新增由本版引入的失败，不能靠汇总平均掩盖退步 |
| 生命周期 | 同一候选版至少 4.3 小时 soak，包含任务中途退出重开和快照恢复；无崩溃、任务丢失、恢复后无法继续；记录内存曲线与失败任务。沿用此前明确接受 4.3 小时的决定，不将它表述为已通过 24 小时 |

除通过率，还报告首任务耗时、授权耗时、重试次数、失败类型、每任务轮数和 token（供应商返回时）。性能数据用相同机器、模型和基准做前后比较；每任务耗时/轮数中位数退步超过 20% 时必须解释原因，不能用不同环境的成绩下结论。

出现未解决的授权卡死、权限重置循环、数据丢失或错误通过的测试，停止发布。修复版不承诺支持所有尚未测到的 macOS 小版本。

## 6. 实施顺序与工作量

假设一名熟悉项目的开发者、可使用第二台 Mac、具备测试 API key 和发布签名。以下是工作量估计，不是交付日期承诺；下载镜像和等待外部设备不计入纯开发日。目前第二台Mac和内置模型测试配置不可用，该原始估算的前提未满足；对应门槛保持未验证。

| 顺序 | 交付物 | 估计 |
|---|---|---|
| 1 | 故障复现、调用时序探针、环境清单；先修测试脚本的退出码 | 1–2 人日 |
| 2 | 单一授权流程、请求去重、reset 边界、弹窗处理与实际截图验证 | 3–4 人日 |
| 3 | 引导失败诊断、手动恢复入口、流程与 fixture 测试 | 1–2 人日 |
| 4 | 双机安装、升级/快照回归、模型任务、soak、文档与发布候选 | 2–3 人日 |

合计 **7–11 人日**，建议分两个候选构建验证。第 1 阶段结束后，根据是否拿到用户同环境修订估计。发布须另获明确指令，编写本规划不等于授权上传 Release。

## 7. 1.0 与 1.1

### 1.0：稳定性放行

0.9.12 验收后，候选版日常使用至少一周，汇总期间反馈；Claude short 两轮全部通过；没有未解决的卡死、丢数据或授权阻塞，再评估发布 1.0。新增已知问题必须回到对应门槛处理。

### 1.1：让已有 agent 更容易、准确地使用这台 Mac

建议只选下面三项作为 1.1 主线，实施前再次检查用户反馈与工作量：

1. **接入现有 coding agent**：在 Coding agents 页输出适用于用户本机路径的 MCP 配置与连通性自检，完成一次“截图—输入—保存—宿主确认”的引导任务。先支持一至两种实际验证的客户端；不把“有 MCP”或“已有 CLI”写成“支持 ACP”。
2. **把现有语义控制做完整**：向 CLI/MCP 补齐可明确指定 app/window 的元素操作、观察版本和可恢复错误；先测 stale target 与跨窗口误操作，再评估性能。目标是在同一任务集上保持成功率，减少坐标重试；收益待实测后再写宣传数字。
3. **任务证据与恢复**：用现有任务事件整理最后成功步骤、失败原因、交付检查和可选截图；提供“从已保存状态继续”的明确入口。仅将支持格式的内容检查标为已验证，不能把存在性校验叫作内容正确性保证。

后续候选：聊天内 agent 切换（先核对各客户端真实支持的协议、登录和取消机制，再实现一个适配器）、默认关闭的 guest `run_shell`、显式选择的剪贴板传递。`run_shell` 需单独设计 guest 范围、超时、输出限额和取消，不能作为未经评估的快捷修复加入。

暂不进入 0.9.12/1.0：跨平台、云端 VM、团队协作、多 VM 并行、分发预授权镜像、替换现有 VM/driver、训练新 agent。没有足够任务或用户证据支持在此阶段承担这些范围。
